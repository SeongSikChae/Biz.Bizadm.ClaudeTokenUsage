### D001 주 단위 보관 기간은 1년으로 한다
- 단계: spec
- 질문: 사용자가 정한 보관 기간에는 분(24시간)·시(1주)·일(1개월)·월(5년)·년(영구)만 있고 주 단위가 빠져 있어, 주 단위 행을 얼마나 보관할지 정해야 했다. 주 단위는 일 단위를 모아 만든다.
- 선택지:
  - A. 5년: 월 단위와 같게 최근 5년을 보관한다. 5년에 약 260개 구간이라 용량 부담이 거의 없다.
  - B. 1년: 최근 52주 정도만 보관하고, 그보다 긴 기간은 월 단위로 본다.
  - C. 영구: 년 단위처럼 지우지 않는다.
- 결정: B. 1년
- 이유: 사용자가 1년을 골랐다. 1년이 넘는 기간은 월·년 단위로 보면 충분하다. A는 주 단위를 5년이나 볼 일이 드물어 고르지 않았고, C는 영구 보관이 필요한 단위는 년 단위로 충분해 고르지 않았다.
- 반영: spec.md C5

### D005 데이터 포인트는 끝 시각이 속한 분 구간에 더한다
- 단계: spec
- 질문: spec 검토 1회차 지적 1. C2의 "포인트의 시각"이 delta 데이터 포인트의 구간 시작 시각과 끝 시각 중 어느 것인지 정하지 않았다. Claude Code는 기본 60초 주기로 내보내므로 한 포인트의 delta 구간이 분 경계를 넘는 경우가 흔하다. 이대로면 같은 포인트가 구현에 따라 다른 분에 들어갈 수 있어 C2의 기대값을 정할 수 없다.
- 선택지:
  - A. 끝 시각 기준: OTLP `time_unix_nano`(KST)가 속한 분 구간에 더한다.
  - B. 시작 시각 기준: `start_time_unix_nano`(KST)가 속한 분 구간에 더한다.
  - 고치지 않음: C2 문구를 그대로 두고 plan에서 정하게 한다.
- 결정: A. 끝 시각 기준
- 이유: OTLP에서 데이터 포인트의 대표 시각은 `time_unix_nano`이고, 방금 내보낸 값이 현재 분에 바로 보인다. B는 값이 늘 한 분 앞 구간에 들어가 끝난 구간으로 늦게 도착하는 값이 더 많아지므로 고르지 않았다. 고치지 않음은 완료 조건의 기대값이 모호하게 남아 고르지 않았다.
- 반영: spec.md C2

### D006 늦게 온 데이터 포인트도 버리지 않고 상위 단위까지 반영한다
- 단계: spec
- 질문: spec 검토 1회차 지적 2. 이미 상위 단위로 모았거나 보관 기간이 지나 지운 구간에 속하는 포인트가 늦게 도착하면 어떻게 할지, "끝난 구간"이 언제부터인지 정의가 없었다. 60초 묶음 전송이라 분이 끝난 뒤 도착하는 값이 실제로 생기며, 분 단위에만 더하면 C3의 "상위 합계 = 하위 합계"가 깨지고 버리면 C2와 어긋난다.
- 선택지:
  - A. 늦은 값도 반영: 그 시각의 분 구간이 보관 기간 안이면 분 행에 더하고 이미 모은 상위 구간을 다시 모은다. 분 보관 기간이 지났으면 그 시각을 아직 보관하는 가장 세밀한 단위부터 위 단위로 더한다. "끝난 구간"은 구간 끝 시각이 지난 구간으로 정의한다.
  - B. 유예 뒤 닫고 버림: 구간 끝에서 5분이 지나면 구간을 닫고, 그 뒤 닫힌 분 구간으로 온 포인트는 저장하지 않고 로그만 남긴다.
  - 고치지 않음: 늦은 데이터 처리와 "끝난 구간" 정의를 두지 않는다.
- 결정: A. 늦은 값도 반영
- 이유: 토큰 사용량 합계를 보는 것이 목적이라 값이 조용히 사라지면 안 된다. B는 단순하지만 시계 차이나 재전송 때 사용량이 빠지므로 고르지 않았다. 고치지 않음은 C2와 C3이 부딪히는 상황을 판정할 수 없어 고르지 않았다.
- 반영: spec.md 용어(끝난 구간), C2

### D007 토큰 종류로 거르면 비용을 돌려주지 않고, 토큰 종류로 나눠 보면 비용은 합계 한 계열로 준다
- 단계: spec
- 질문: spec 검토 1회차 지적 3. `claude_code.cost.usage`에는 `type`(토큰 종류) 속성이 없는데, C7·C8은 토큰 종류로 거르거나 나눠 볼 수 있게 하면서 그때 비용을 무엇으로 보일지 정하지 않았다. input만 걸러 봤는데 비용은 전체 값이 나오는 혼동이 생길 수 있다.
- 선택지:
  - A. 필터 시 비용 숨김: 토큰 종류 필터를 걸면 비용을 돌려주지 않는다(null). 나눠 볼 기준이 토큰 종류이면 비용은 구간 합계 한 계열로 돌려준다. 화면에 토큰 종류로 거르면 비용을 볼 수 없다는 안내를 표시한다.
  - B. 비용은 필터 무시: 비용은 토큰 종류 필터·나눠 보기와 상관없이 사용자·모델 필터만 적용한 구간 합계로 돌려주고, 화면에 토큰 종류 필터 미적용임을 표시한다.
  - 고치지 않음: 토큰 종류 필터·나눠 보기 때 비용 출력을 정하지 않는다.
- 결정: A. 필터 시 비용 숨김
- 이유: 걸러지지 않은 값을 걸러진 토큰과 같은 화면에 보이는 것보다, 보이지 않는 쪽이 오해가 적다. B는 표시가 있어도 걸러진 토큰과 걸러지지 않은 비용을 나란히 보며 혼동하기 쉬워 고르지 않았다. 고치지 않음은 C7·C8의 비용 출력을 검증할 수 없어 고르지 않았다.
- 반영: spec.md C7, C8

### D008 늦게 온 값은 이미 모은 상위 구간에 증분으로 더하고, C3 등식은 하위 행이 모두 보관 중인 상위 구간에만 적용한다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. C5의 삭제 기준선이 하위 단위 기준이라 상위 구간 경계와 맞지 않아, 상위 구간 하나에 하위 행 일부만 남는 상태가 늘 생긴다(예: 11-20 14:37이면 11-19 14:00 시 구간의 분 행 중 14:00~14:36은 지워지고 14:37~14:59는 남음). 이때 C3("하위 행이 아직 보관 중인 끝난 구간에서 상위 합계 = 하위 행 합계")과 C5("지워도 상위 합계는 바뀌지 않음")가 함께 성립할 수 없다. 또 C2의 "이미 모은 상위 구간을 다시 모은다"를 남은 하위 행으로 다시 합산하는 것으로 구현하면, 이미 지운 분의 값이 시 합계에서 빠진다.
- 선택지:
  - A. 증분 반영 + C3 한정: C2의 "다시 모은다"를 "이미 모은 상위 구간에도 그 값을 더한다(남은 하위 행으로 다시 합산하지 않음)"로 바꾸고, C3을 "그 구간에 들어가는 하위 단위 행이 모두 보관 중인 끝난 상위 구간"으로 한정한다.
  - B. 삭제를 상위 경계에 맞춤: 하위 행은 그 행이 속한 상위 구간 전체가 보관 기간을 지났을 때 한꺼번에 지운다(분은 시 구간, 시는 일 구간, 일은 주·월 구간 기준). 하위 행이 일부만 남는 상위 구간이 생기지 않으므로 다시 합산해도 맞다.
  - 고치지 않음: C2·C3 문구를 그대로 둔다.
- 결정: A. 증분 반영 + C3 한정
- 이유: 보관 기간이 사용자가 정한 값 그대로 유지되고 문구 두 곳만 바뀐다. B는 실제 보관 기간이 상위 구간 길이만큼 늘어나고(일 행은 최대 한 달 더), 주와 월 경계가 서로 달라 일 행 삭제 규칙이 복잡해지므로 고르지 않았다. 고치지 않음은 완료 조건끼리 모순되고 합계가 줄 수 있어 고르지 않았다.
- 반영: spec.md C2, C3

### D009 조회 기간 안에서 사용량이 없는 구간은 0으로 채운다
- 단계: spec
- 질문: spec 검토 2회차 지적 4. 1회차 수정으로 C7이 "보관 기간이 지나 행이 없는 구간은 응답에 넣지 않는다"로 좁혀져, 보관 기간 안이지만 사용량이 없어 행이 없는 구간을 응답에 0으로 채워 넣을지 뺄지 알 수 없게 됐다. 응답 시계열의 길이와 차트 x축의 빈 구간 표시를 정할 수 없다.
- 선택지:
  - A. 빈 구간 0으로 채움: 보관 기간 안에서 사용량이 없는 구간은 0으로 채워 넣고, 보관 기간이 지난 구간은 응답에 넣지 않는다.
  - B. 빈 구간은 모두 뺌: 행이 없는 구간은 사용량이 없어서든 보관 기간이 지나서든 응답에 넣지 않는다.
  - 고치지 않음: 보관 기간 안 빈 구간 처리를 정하지 않는다.
- 결정: A. 빈 구간 0으로 채움
- 이유: 사용량이 없던 시간대가 차트에 0으로 드러나 x축이 연속되어 시간 흐름을 읽기 쉽다. B는 차트에서 빈 구간이 건너뛰어 보여 시간 흐름을 읽기 어려우므로 고르지 않았다. 고치지 않음은 응답 기대값을 정할 수 없어 고르지 않았다.
- 반영: spec.md C7

### D010 받은 값은 2분 안에 모든 단위 조회에 반영되면 된다
- 단계: spec
- 질문: spec 검토 2회차 지적 5. 롤업은 1분마다 처리하고 C3은 끝난 구간만 다루므로, C7의 "아직 끝나지 않은 현재 구간도 그때까지 받은 값으로 포함한다"가 받은 즉시 시·일·주·월·년 조회에 보여야 한다는 뜻인지, 몇 분 늦어도 되는지 정해지지 않았다. 지표를 보낸 직후 주·월 단위로 조회하는 테스트를 판정할 수 없다.
- 선택지:
  - A. 즉시 반영: 받은 값은 응답을 돌려준 뒤 바로 모든 단위의 조회 결과(현재 구간 포함)에 반영된다.
  - B. 2분 안에 반영: 받은 값은 받은 뒤 2분 안에 모든 단위의 조회 결과(현재 구간 포함)에 반영된다.
  - 고치지 않음: 반영 시점을 정하지 않는다.
- 결정: B. 2분 안에 반영
- 이유: Claude Code가 기본 60초마다 지표를 보내므로 1~2분 지연은 쓰임에 지장이 없고, 1분 주기 처리로 단순하게 맞출 수 있다. A는 현재 구간을 조회할 때 하위 단위까지 더해 보여 주는 등의 처리가 필요해 구조가 복잡해지므로 고르지 않았다. 고치지 않음은 C7의 현재 구간 포함 요구를 판정할 수 없어 고르지 않았다.
- 반영: spec.md C7

### D011 현재 구간보다 뒤인 미래 구간은 조회 응답에 넣지 않는다
- 단계: spec
- 질문: spec 검토 3회차 지적 1. D009로 "보관 기간 안에서 사용량이 없는 구간은 0으로 채운다"가 들어온 뒤, 조회 끝이 현재 구간보다 뒤일 때(예: 이번 달 전체를 일 단위로 보기) 그 미래 구간을 0으로 채워 응답에 넣을지, 현재 구간에서 잘라 뺄지 정해지지 않았다. C5의 삭제 기준으로 읽으면 미래 구간도 "보관 기간 안"이 된다. 응답 계열 길이와 차트 x축에 미래 구간이 나오는지를 판정할 수 없다.
- 선택지:
  - A. 현재 구간에서 자름: 현재 구간보다 뒤인 구간은 응답에 넣지 않는다. 끝은 미래로 골라도 된다.
  - B. 미래도 0으로 채움: 현재 구간보다 뒤인 구간도 고른 끝까지 0으로 채워 넣는다.
  - 고치지 않음: 미래 구간 처리를 정하지 않는다.
- 결정: A. 현재 구간에서 자름
- 이유: 아직 오지 않은 시간을 0으로 보이면 사용량이 없었던 것으로 잘못 읽힌다. B는 x축 범위가 고른 기간으로 고정되는 이점이 있지만 미래가 사용량 0으로 오해될 수 있어 고르지 않았다. 고치지 않음은 끝이 미래인 조회의 응답 길이를 판정할 수 없어 고르지 않았다.
- 반영: spec.md C7

### D012 .NET 10 SDK를 설치하고 global.json으로 고정한다
- 단계: plan
- 질문: 규칙 `dotnet/project-creation.md`는 TFM `net10.0`과 .NET 10 계열 SDK를 쓰라고 정하고, 템플릿 스킬은 SDK 10이 없으면 보고하고 중단하라고 정한다. 이 PC에는 SDK 11.0.100만 있고 런타임은 10.0.15와 11.0.0이 있어, 어떤 SDK·TFM으로 만들지 정해야 했다.
- 선택지:
  - A. SDK 10 설치: 구현 전에 사용자가 .NET 10 SDK(10.0.1xx 최신)를 설치하고, 저장소에 `global.json`(sdk 10.0.100, rollForward latestFeature)을 두며 TFM은 net10.0이다.
  - B. SDK 11로 net10.0 빌드: 설치 없이 SDK 11.0.100으로 TFM net10.0 프로젝트를 빌드하고, 원칙 점검에 SDK 규칙을 따르지 않는 이유를 적는다.
  - C. net11.0으로 대상 변경: TFM을 net11.0으로 하고 Microsoft.* 패키지를 11.0.x로 올린다.
- 결정: A. SDK 10 설치
- 이유: 규칙과 템플릿을 그대로 따르고, 다른 PC·CI에서도 같은 SDK로 빌드된다. B는 바로 진행할 수 있지만 SDK 11의 분석기·기본값 차이로 경고가 달라질 수 있고 규칙과 어긋나 고르지 않았다. C는 규칙의 TFM·SDK가 모두 어긋나고 Biz.Bizadm.* 패키지가 net11에서 검증되지 않아 고르지 않았다.
- 반영: plan.md 바꿀 파일(`global.json`), 결정, 원칙 점검

### D013 서비스 연동은 AddWindowsService·AddSystemd로 한다
- 단계: plan
- 질문: 사용자는 `UseWindowsService`·`UseSystemd` 도입을 요청했다(spec C10). 그런데 `Host.UseWindowsService()`는 Windows 서비스로 실행될 때 콘텐츠 루트를 실행 파일 폴더(`AppContext.BaseDirectory`)로 바꾸려 한다. 템플릿은 콘텐츠 루트를 YAML `ContentRootPath`로 정하므로, 두 값이 다르면 `WebApplicationBuilder`가 예외를 내고 서비스가 시작되지 않는다. 어느 API로 서비스 연동을 할지 정해야 했다.
- 선택지:
  - A. AddWindowsService/AddSystemd: `builder.Services.AddWindowsService()`와 `builder.Services.AddSystemd()`를 쓴다. 서비스 시작·중지 연동과 이벤트 로그·journald 형식은 UseXxx와 같고, 콘텐츠 루트는 YAML 그대로 둔다. spec C10의 `UseWindowsService`·`UseSystemd` 표기는 같은 기능의 Add 형태로 구현한다고 plan에 적는다.
  - B. UseWindowsService/UseSystemd: `builder.Host.UseWindowsService()`와 `builder.Host.UseSystemd()`를 쓰고, README에 Windows 서비스로 실행할 때는 YAML `ContentRootPath`를 실행 파일 폴더와 같게 두라고 적는다.
- 결정: A. AddWindowsService/AddSystemd
- 이유: YAML로 정한 콘텐츠 루트(DuckDB 파일·ClientApp 위치)와 충돌하지 않는다. B는 콘텐츠 루트를 다른 폴더로 두면 서비스 시작이 실패해 배포에 제약이 생기므로 고르지 않았다.
- 반영: plan.md 결정, `Program.cs` 항목, 원칙 점검

### D015 Linux systemd 서비스의 KEK 저장소는 gpg로 안내한다
- 단계: 구현 후 수동 검증(C10 Linux)
- 질문: Rocky Linux 9 서버에서 systemd 확인을 준비하며, OsKms KEK의 Linux 기본 저장소가 데스크톱 키링(Secret Service)이라 서비스에서는 쓸 수 없다는 것을 확인했다. 검증과 배포 안내에 어느 저장소를 쓸지 정해야 했다.
- 선택지:
  - A. 기본으로 먼저 띄워 보고 판단: 실패를 확인한 뒤 고칠 방법을 다시 정한다.
  - B. gpg 저장소: `GCM_CREDENTIAL_STORE=gpg`로 서비스 계정의 gpg 키와 pass 형식 저장소에 둔다.
- 결정: B. gpg 저장소
- 이유: 서비스에는 D-Bus 세션·키링이 없어 기본 저장소는 실패가 거의 확실하다. gpg 저장소는 배포판 기본 패키지(`gnupg2`)만으로 쓸 수 있고 KEK가 평문으로 남지 않는다. 검증 중 gpg 저장소가 `GPG_TTY`를 요구해 첫 기동이 종료 코드 2로 실패했고, `GPG_TTY=/dev/null`(암호 없는 키라 터미널을 쓰지 않음)을 더해 시작·재시작·중지를 확인했다. 사용자가 README·유닛 예시에 이 안내를 추가하라고 했다.
- 반영: `deploy/systemd/biz-bizadm-claudetokenusage.service`(`GCM_CREDENTIAL_STORE`, `GPG_TTY`), README "systemd"(gpg 키·저장소 준비 절차), plan.md README 내용·오류와 위험·검증 전략, tasks.md T031
