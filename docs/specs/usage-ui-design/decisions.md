### D001 차트 계열 색을 서로 구분되는 색상 팔레트로 바꾼다
- 단계: spec
- 질문: 지금 차트 계열 색이 회색 명도 단계(`--chart-1`~`--chart-5`)뿐이라 input·output·cacheRead 같은 계열이 거의 구분되지 않는다(실제 화면에서 output 막대가 사실상 보이지 않음). 계열 색을 어떻게 바꿀지 정해야 했다.
- 선택지:
  - A. 구분되는 색상 팔레트: 파랑·주황·청록·보라·분홍 등 서로 다른 색상 8개 정도로 바꾸고 다크 모드용 값도 둔다.
  - B. 한 색의 명도 단계: 파랑 계열 하나를 밝기만 달리 써서 차분하게 유지한다.
- 결정: A
- 이유: A는 계열이 많아도 색상으로 구분된다. B는 계열이 4개를 넘으면 지금의 회색 단계와 같은 이유로 구분이 다시 어려워진다.
- 반영: spec.md C1

### D004 차트 라이브러리를 Recharts에서 Apache ECharts로 바꾼다
- 단계: spec
- 질문: D003의 E에 따라 차트 라이브러리를 지금의 Recharts(shadcn chart 래퍼)에서 Apache ECharts로 바꿀지 정해야 했다.
- 선택지:
  - A. ECharts로 교체: 토큰 누적 막대와 비용 막대를 ECharts로 다시 만들고, 두 차트의 X축 확대·툴팁을 연동하며 범례 클릭으로 계열을 켜고 끈다. 번들이 약 300~400KB(gzip 약 120KB) 늘고, jsdom에는 canvas가 없어 차트 내부는 단위 테스트로 보지 못한다.
  - B. Recharts 유지: 라이브러리는 두고 색·축·비용 차트 분리·레이아웃만 다듬는다. 범례 토글은 직접 구현한다.
- 결정: A
- 이유: A는 두 차트 연동, 구간 확대, 범례 토글이 기본 기능이라 사용자가 요청한 현대적인 차트에 맞고, 분 단위 24시간(1,440구간)도 canvas로 가볍게 그린다. B는 변경이 작고 번들이 늘지 않지만 확대·연동 같은 상호작용이 빈약해 요청을 덜 채운다.
- 반영: spec.md C2·C3·C4

### D005 자동 갱신은 헤더의 '실시간' 토글로 켜고 끈다
- 단계: spec
- 질문: 사용자가 페이지를 열어 두면 10초마다 자동 갱신되기를 요청했다. 그런데 지금 기간의 끝(`to`)은 화면을 열거나 단위를 바꾼 순간(지금+1분)에 고정되고, 조회 API는 끝 뒤의 구간을 돌려주지 않는다(token-usage R7). 그래서 기간을 그대로 두고 다시 조회만 하면 1분 남짓 뒤부터 새 구간이 화면에 나오지 않는다. 자동 갱신 때 기간을 어떻게 다룰지 정해야 했다.
- 선택지:
  - A. 기본 기간이면 지금을 따라감: 기간을 직접 바꾸지 않았으면 갱신마다 그 단위의 기본 기간을 지금 기준으로 다시 잡고, 시작·끝을 직접 고르면 그 기간을 그대로 다시 조회한다.
  - B. '실시간' 토글로 선택: 헤더에 실시간 토글을 두고, 켜면 10초마다 기간을 지금 기준으로 밀어 조회한다. 끄면 자동 갱신도 멈춘다.
  - C. 기간은 그대로 다시 조회: 고른 기간을 바꾸지 않고 같은 조건으로 다시 조회만 한다. 끝 뒤의 새 구간은 보이지 않는다.
- 결정: B
- 이유: 사용자가 골랐다. B는 자동 갱신과 기간 이동이 켜져 있는지 화면에서 분명히 보이고 사용자가 직접 켜고 끌 수 있다. A는 조작은 없지만 직접 고른 기간인지 기본 기간인지가 화면에 드러나지 않는다. C는 끝을 미래로 고르지 않으면 자동 갱신의 효과가 거의 없다.
- 반영: spec.md C11

### D007 새로고침 버튼은 실시간 토글 상태에 따라 기간을 옮기거나 그대로 둔다
- 단계: spec
- 질문: spec 검토 1회차 지적 1. 검토 의견은 C7이 새로고침하면 "지금 필터로 다시 조회한다"고만 해서, 기간 끝(`to`)이 화면을 연 순간에 고정된 채 다시 조회하면 새 구간이 나오지 않을 수 있다는 것이다. 자동 갱신은 C11(실시간 토글)로 정리됐지만 새로고침 버튼의 기간 처리는 정해지지 않아 구현마다 달라지고 C7을 판정할 수 없었다.
- 선택지:
  - A. 토글 따라 다르게: 실시간이 켜져 있으면 C11과 같이 기간을 지금 기준으로 옮겨 조회하고, 꺼져 있으면 고른 기간 그대로 다시 조회한다.
  - B. 항상 지금으로 옮김: 새로고침은 토글과 상관없이 기간을 지금 기준으로 옮겨 조회한다.
- 결정: A
- 이유: A는 C11과 같은 규칙이라 일관되고, 직접 고른 기간이 버튼 한 번에 덮어써지지 않는다. B는 실시간을 꺼 두고 직접 고른 과거 기간이 버튼 한 번에 바뀌어 버린다.
- 반영: spec.md C7

### D008 범례로 숨긴 계열은 툴팁 합계에서만 빼고 요약에는 반영하지 않는다
- 단계: spec
- 질문: spec 검토 1회차 지적 3. 검토 의견은 C4로 계열을 숨겼을 때 C5 툴팁의 구간 토큰 합계와 C6 요약의 계열별 합계·비율에 반영하는지가 없다는 것이다. 응답의 `totalTokens`·`totals.tokens`는 숨김과 상관없어 두 해석이 모두 가능하므로 숫자가 구현마다 달라지고 C5·C6을 검증할 기준이 없었다.
- 선택지:
  - A. 툴팁만 보이는 계열: 툴팁의 구간 토큰 합계는 숨기지 않은 계열만 더하고, 요약은 숨김과 상관없이 고른 기간 전체다.
  - B. 둘 다 전체: 툴팁·요약 모두 숨김과 상관없이 전체 합계다.
  - C. 둘 다 보이는 계열: 툴팁·요약 모두 숨긴 계열을 빼고 다시 계산한다.
- 결정: A
- 이유: A는 툴팁 합계가 차트에 보이는 막대 높이와 맞고, 요약은 필터로 정한 기간의 사실을 그대로 보인다. B는 계열을 숨겨도 툴팁 합계가 보이는 막대보다 커서 혼동된다. C는 요약의 토큰 총합이 필터가 아닌 차트 조작에 따라 바뀌고, 계열별로 나눌 수 없는 비용 총합과 어긋난다.
- 반영: spec.md C5, C6

### D010 자동 갱신 중 확대 범위는 전체 기간 대비 비율로 유지한다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. 검토 의견은 C11이 갱신마다 기간을 지금 기준으로 옮겨 구간 목록이 밀리는데, "확대 범위 유지"가 같은 시각의 구간을 계속 보여 주는 것인지 같은 상대 위치를 유지해 최신을 따라가는 것인지 없다는 것이다. 두 해석에서 갱신 뒤 보이는 구간이 달라 구현마다 갈리고 판정 기준이 없었다.
- 선택지:
  - A. 상대 위치 유지: 확대 범위를 전체 기간 대비 같은 비율로 유지해, 오른쪽 끝을 보고 있었으면 최신 구간을 따라간다. 확대하지 않았으면 전체 기간을 본다.
  - B. 같은 시각 고정: 확대한 시각 범위를 그대로 보여 주고, 그 범위가 기간 밖으로 밀려나면 확대를 푼다.
- 결정: A
- 이유: A는 실시간 화면의 목적(최신 값 보기)에 맞고 ECharts 확대 기능의 기본 동작(비율)과 같다. B는 특정 시각을 살펴보기엔 좋지만 최신 값을 보려면 매번 다시 확대해야 하고 구현이 더 복잡하다.
- 반영: spec.md C11

### D011 실시간을 다시 켜면 곧바로 기간을 지금 기준으로 옮겨 조회한다

- 반영: spec.md C11

### D012 계열 색과 범례 숨김을 계열 이름에 묶고, 정한 색은 페이지를 다시 열 때까지 유지한다
- 단계: spec
- 질문: spec 검토 2회차 지적 3. 검토 의견은 자동 갱신으로 응답의 계열 목록이 바뀔 수 있는데 색과 숨김이 무엇에 묶이는지 없다는 것이다. 지금 코드(`UsageChart.tsx`)는 계열 순서(`s${index}`)로 색과 키를 매겨, 새 계열이 앞에 끼어들면 뒤 계열의 색과 숨김 대상이 한 칸씩 밀린다. 이제 조작 없이 10초마다 생길 수 있는 결함이다.
- 선택지:
  - A. 이름에 묶고 색 유지: 색과 숨김을 계열 이름에 묶고, 한 번 정한 색은 페이지를 다시 열 때까지 유지하며 새 계열은 다음 색을 받는다.
  - B. 숨김만 이름, 색은 매번 순서: 숨김은 이름에 묶고 색은 응답 순서대로 매번 다시 매긴다.
- 결정: A
- 이유: A는 보던 계열의 색과 숨김이 갱신 중에 바뀌지 않는다. B는 새 계열이 끼어들면 보던 계열의 색이 갑자기 바뀐다.
- 반영: spec.md C1, C4

### D013 색 배정은 기준·필터를 바꾸면 처음부터 다시 하고, 갱신 중 새 계열은 화면에서 쓰지 않는 색을 받는다
- 단계: spec
- 질문: D012 대체. spec 검토 3회차 지적 1. 검토 의견은 D012대로 색 순번을 페이지를 연 동안 나타난 모든 계열 이름에 누적하면, 나눠 볼 기준(모델·사용자·토큰 종류)을 몇 번 바꾸는 사이 순번이 8을 넘어 팔레트가 돌고, 한 화면에 계열이 2~3개뿐인데도 두 막대가 같은 색을 받을 수 있다는 것이다. C1의 "8개까지 서로 다른 색"을 판정할 수 없고 계열 구분이라는 C1의 목적이 다시 깨진다.
- 선택지:
  - A. 조작 시 초기화와 빈 색: 나눠 볼 기준이나 사용자·모델·토큰 종류 필터를 바꾸면 색을 응답 순서대로 다시 매긴다. 그 밖의 갱신(자동 갱신·새로고침·기간 변경)에서는 계열 이름별 색을 유지하고, 새로 나타난 계열은 지금 화면의 계열이 쓰지 않는 색 가운데 가장 앞 번호를 받는다(모두 쓰고 있으면 처음부터).
  - B. 기준별 색 기억: 나눠 볼 기준마다 색 배정을 따로 기억하고 그 안에서는 누적한다.
- 결정: A
- 이유: A는 화면 계열이 8개 이하면 늘 서로 다른 색이라 판정 기준이 분명하고, 갱신 중에 보던 계열의 색이 바뀌지 않는다는 D012의 목적도 지킨다. B는 기준을 오갈 때의 문제는 줄지만, 같은 기준에서 필터를 오가며 이름이 8개 넘게 쌓이면 적은 계열에서도 같은 색이 여전히 나온다.
- 반영: spec.md C1

### D014 계열 색은 지금 응답에 있는 계열만 가진다
- 단계: spec
- 질문: spec 검토 4회차 지적 1. 검토 의견은 D013대로 "이름별 색 유지"와 "지금 화면의 계열이 쓰지 않는 색"의 범위가 달라, 응답에서 빠진 계열이 색을 계속 갖는지와 범례로 숨긴 계열이 "지금 화면의 계열"에 들어가는지가 없다는 것이다. 예를 들어 A=1번, B=2번에서 B가 빠지고 C가 나타나면 C가 2번을 받고, 그 뒤 B가 다시 나타나 유지된 2번을 쓰면 계열 3개에서 B와 C가 같은 색이 된다. 실시간 기간 이동으로 계열이 빠졌다 다시 나타나는 일이 흔해 "8개 이하면 서로 다른 색"이 깨진다.
- 선택지:
  - A. 지금 응답 계열만 색 보유: 색은 지금 응답에 있는 계열(범례로 숨긴 계열 포함)만 가지며, 응답에서 빠진 계열은 색을 잃고 다시 나타나면 새로 나타난 계열로 본다. "지금 화면의 계열"은 지금 응답의 계열 전부다.
  - B. 빠진 계열도 색 예약: 빠진 계열의 색을 예약해 다시 나타나면 같은 색을 주고, 새 계열은 예약되지 않은 색을 받는다(예약이 8개를 넘으면 가장 오래 빠진 계열의 예약을 푼다).
- 결정: A
- 이유: A는 판정 기준이 "지금 응답" 하나로 모이고 계열 8개 이하면 늘 서로 다른 색이 보장된다. 대신 다시 나타난 계열의 색은 전과 달라질 수 있다. B는 다시 나타난 계열의 색이 유지되지만 규칙이 복잡하고, 예약을 풀 때 다시 겹치는 경우가 생겨 판정이 어렵다.
- 반영: spec.md C1

### D015 비용 차트 유무가 바뀔 때만 차트 옵션을 새로 그린다
- 단계: plan
- 질문: plan 검토 1회차 지적 1. 검토 의견은 옵션 갱신 때 `series`만 `replaceMerge`하고 나머지를 ECharts 기본 병합에 맡기면, 비용이 있다가 없어질 때(토큰 종류 필터를 켤 때) 두 번째 그리드와 `$` 비용 축이 지워지지 않고 남는다는 것이다. ECharts 기본 병합은 배열 컴포넌트를 인덱스별로 합쳐 새 옵션에 없는 뒤 항목을 남기므로 C2가 가장 흔한 경로에서 깨지고, 순수 함수 단위 테스트로는 드러나지 않는다.
- 선택지:
  - A. 모양이 바뀔 때만 notMerge: 비용 차트 유무(그리드 수)가 이전 옵션과 다르면 `setOption(option, { notMerge: true })`로 새로 그리고 확대 범위는 0~100으로 돌아간다. 같으면 `replaceMerge: ['series']`로 갱신한다.
  - B. 축·그리드도 늘 replaceMerge: `replaceMerge: ['series', 'grid', 'xAxis', 'yAxis']`로 늘 교체하고 `dataZoom`은 `start`/`end` 없이 축 번호만 넘겨 비율을 유지한다.
- 결정: A
- 이유: A는 동작이 확정적이고, 확대가 처음으로 돌아가는 때는 사용자가 토큰 종류 필터를 바꿀 때뿐이다(비용 null은 그때만 생김, token-usage R7). 그래서 자동 갱신 중의 확대 유지(C11)와 부딪히지 않는다. B는 필터를 바꿔도 확대가 유지되지만, 교체된 축과 `dataZoom`의 연결이 ECharts 내부 동작에 기대 덜 확실하다.
- 반영: plan.md 바꿀 파일(UsageChart.tsx), 결정, 검증 전략 C2

### D016 ECharts에 넘기는 색은 hex CSS 변수로 정의한다
- 단계: plan
- 질문: plan 검토 1회차 지적 2. 검토 의견은 `index.css`의 색 토큰이 모두 `oklch(...)`라 `getComputedStyle`로 읽으면 oklch 문자열이 그대로 나오는데, ECharts가 마우스를 올린 막대의 강조색을 계산하는 zrender 색 해석기는 hex·rgb·hsl·이름 색만 읽어 oklch를 해석하지 못하고, 그 결과 가리킨 막대가 투명해진다는 것이다. C1·C3을 쓰는 순간 드러나고 jsdom 테스트로는 보이지 않는다.
- 선택지:
  - A. 차트용 색을 hex 변수로: ECharts에 넘기는 색(`--series-1`~`--series-8`, `--chart-cost`, `--chart-axis`, `--chart-grid`)을 라이트·다크 각각 hex로 정의하고, 범례·요약 같은 DOM도 같은 변수를 쓴다.
  - B. oklch→sRGB 변환 함수: 읽은 oklch 값을 `rgb()`로 바꾸는 함수(테스트 포함)를 거쳐 ECharts에 넘긴다.
- 결정: A
- 이유: A는 단순하고 확정적이며, 팔레트는 어차피 새로 정의한다. B는 기존 토큰을 재사용할 수 있지만 색 공간 변환 코드와 테스트가 늘고 알파·범위 밖 값 같은 경계 처리가 생긴다.
- 반영: plan.md 바꿀 파일(index.css), 결정, 인터페이스·데이터, 검증 전략 C1·C3

### D017 테마는 클래스를 먼저 바꾸는 외부 저장소로 관리한다
- 단계: plan
- 질문: plan 검토 2회차 지적 1. 검토 의견은 차트가 테마 값 변경을 계기로 CSS 변수를 다시 읽는데, 변수 값은 `<html>.dark` 클래스가 실제로 바뀐 뒤에야 바뀌고 plan이 그 순서를 정하지 않았다는 것이다. 클래스를 훅의 `useEffect`에서 바꾸면 React가 자식(`UsageChart`)의 effect를 부모(`App`)보다 먼저 실행해 차트가 이전 테마 값을 읽는다. 토글 때 차트 색이 한 단계 늦게 바뀌어 C8이 깨지고, 계획한 자동 검증으로는 드러나지 않는다.

### D018 조회 오류는 성공할 때만 지우고, 조회에 15초 시간 제한을 둔다
- 단계: plan
- 질문: plan 검토 4회차 지적 2. 검토 의견은 지금 `usageSlice.ts`의 `loadSeries.pending`이 요청마다 `error`를 지워, 실시간이 켜진 채 실패가 이어지면 오류 문구가 10초마다 사라졌다 나타나고, `api.ts`의 `fetch`에 시간 제한이 없어 서버가 응답 없이 멈추면 오류가 거의 또는 전혀 보이지 않는다는 것이다. plan의 "다음 주기에 성공하면 오류가 사라진다" 전제가 지금 리듀서와 다르고 C7("조회가 실패하면 오류를 보인다")이 실시간 중 지켜지지 않는다.
- 선택지:
  - A. 성공 때만 지움 + 15초 제한: `loadSeries.pending`은 `error`를 지우지 않고 `fulfilled`에서만 지운다. `getJson`의 `fetch`에 `AbortSignal.timeout(15000)`을 두고 시간 초과는 "응답 시간이 초과되었습니다" 오류로 바꾼다.
  - B. 성공 때만 지움: `pending`에서 오류를 지우지 않는 것만 고친다.
- 결정: A
- 이유: A는 오류가 깜빡이지 않고, 서버가 멈춘 경우도 실패로 보여 C7을 채운다. B는 깜빡임은 없어지지만 서버가 응답 없이 멈추면 오류가 표시되지 않는다.
- 반영: plan.md 바꿀 파일(usageSlice.ts, api.ts), 오류·위험, 검증 전략 C7

### D019 자동 갱신 타이머는 조회 중이면 그 주기를 건너뛴다
- 단계: plan
- 질문: plan 검토 5회차 지적 1. 검토 의견은 시간 제한(15초)이 갱신 주기(10초)보다 길어 시간 초과 전에 다음 요청이 나가고, 슬라이스는 `pending`마다 `seriesRequestId`를 새 요청으로 바꾸고 다른 요청의 `rejected`를 버리므로, 서버가 멈춘 동안 시간 초과되는 요청은 늘 "앞선 요청"이 되어 무시된다는 것이다. 화면은 오류 없이 계속 조회 중으로 남아, 실시간이 기본으로 켜진 가장 흔한 상태에서 C7이 깨지고 D018이 효과를 내지 못한다.

  - B. 시간 제한 8초: 시간 제한을 갱신 주기보다 짧은 8초로 줄인다.
- 결정: A
- 이유: A는 느리지만 정상인 응답은 받고, 자동 갱신이 겹치지 않아 서버가 멈추면 15초 뒤 오류를 확실히 보인다. B는 구현이 단순하지만 8초를 넘는 느린 정상 응답도 실패가 되고, 주기와 제한의 크기 관계에 기대어 숫자를 바꾸면 다시 깨진다.
